# CRDs shipped with the `llm-gateway-apikey` chart

The chart ships exactly one CRD — its own `APIKey` — and it does **not** live
in a `crds/` directory.

The Istio CRDs (`EnvoyFilter`, `PeerAuthentication`) the chart's templates
under `templates/istio/` depend on are **not** bundled. Install them with
Istio itself, before installing this chart.

## Where the APIKey CRD lives

`apikeys.kaito.sh` ships from `templates/kaito.sh_apikeys.yaml`, as an
ordinary chart template rather than a `crds/` entry.

It lives there because Helm's `crds/` directory is **create-on-install-only**:
`helm upgrade` skips it entirely. It does not update an existing CRD, and it
does not even re-create a deleted one. Any schema change — a new field, a new
served version, a tightened validation rule — would silently never reach a
cluster that already has the chart installed.

That is especially bad wherever the `helm upgrade` is run for you rather than
by hand — a GitOps controller, an operator, or any packaging layer that
installs this chart as a subchart. In those setups there is no opportunity to
`kubectl apply` an updated CRD out of band first.

As a template the CRD is part of the release manifest, so `helm upgrade`
applies schema changes like any other resource. It carries:

```yaml
annotations:
  helm.sh/resource-policy: keep
```

which stops `helm uninstall` from deleting the CRD — and with it every
`APIKey` in the cluster — when the release goes away.

**Do not edit the CRD by hand,** and do not add the annotation by hand. Both
are generated by:

```sh
make manifests
```

which runs `controller-gen` against `api/v1alpha1/` and writes the result into
`templates/`. The `helm.sh/resource-policy: keep` annotation comes from a
`+kubebuilder:metadata:annotations` marker on the `APIKey` type, so it survives
regeneration. To change the CRD schema, edit the Go types in `api/v1alpha1/`
and re-run `make manifests`, then commit the result.

The filename follows controller-gen's `{group}_{plural}.yaml` convention.

### Upgrading a cluster installed before this change

Clusters that installed the CRD from `crds/` have a CRD with **no Helm
ownership metadata**. Helm refuses to adopt such a resource into a release and
the upgrade fails with:

```
invalid ownership metadata; label validation error: missing key
"app.kubernetes.io/managed-by": must be set to "Helm"
```

Stamp the metadata once, before upgrading:

```sh
kubectl label crd apikeys.kaito.sh app.kubernetes.io/managed-by=Helm --overwrite
kubectl annotate crd apikeys.kaito.sh \
  meta.helm.sh/release-name=<release> \
  meta.helm.sh/release-namespace=<namespace> --overwrite
```

`<release>` is the **owning Helm release** — when this chart is installed as a
subchart, that is the parent umbrella's release name, not
`llm-gateway-apikey`. Read it off the cluster with `helm list -A` rather than
assuming.

`hack/setup-test-env.sh` does this automatically, so local kind clusters
reused across the move adopt the CRD without manual steps.
